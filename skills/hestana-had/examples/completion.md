# Readiness and completion examples

All contracts, candidates, actors and observations are fictional. They illustrate [readiness and completion](../references/readiness-and-completion.md); no check, deployment, acceptance or authority assignment occurred.

## Capture is useful before implementation is ready

Captured title: "Let me reopen my usual task filter." The next discovery action is ready when context access is authorized and the assistant can ask about the difficulty. Implementation is not ready: ownership behaviour and the save/reopen contract are unresolved. The idea is recorded without a full template or an open status; an open status cannot supply a missing decision, input or reservation.

## A reviewed candidate can finish before a separately scoped release

Contract C1 revision 2 promises a reviewed personal-filter candidate, deployment excluded. Fictional repository policy RP1 revision 7 supplies code, review and integration obligations. Candidate c17, recorded in C1's task result and comments:

- Save/reopen on c17 in fixture environment T1: original supported values restored after reload.
- Failed save: current filter preserved, agreed error and retry shown, no success.
- Isolation: another actor and another project get the same non-disclosing response as a missing identifier.
- RP1's quality and integration checks and review: passed on c17; verifier Sam at t3, no outstanding findings.
- Fixture acceptor Alex accepts C1 revision 2 / c17 at t4.

C1 can finish. Its result says "reviewed candidate accepted; not deployed". A release consumer can require accepted c17, which does not mean C1 promised live availability. Any required repository integration checkpoint stays part of C1 despite the deployment exclusion.

## Local success does not complete a live-outcome promise

Outcome O1 promises the same feature usable by authorized members live. It has the candidate evidence plus a deployment request accepted by a queue. O1 is not complete: the queue response does not establish the running revision, readiness, authenticated behaviour or the isolation and failure checks. If O1 also promised reduced repeat setup against a baseline, that measurement remains unverified until the agreed observation exists; do not invent a target or window.

## A tiny code fix keeps its repository obligations

The one-task fix that removes a duplicate heading is still a repository change. The executor loads current repository instructions, records the references observed and runs the required checks and review. If the UI check passes but a mandatory gate fails or cannot run, the result is not complete: record the failure or gap and the next action. "Small fix" is not an exemption.

## Research can complete with an unresolved downstream choice

Investigation R1 promises a bounded report on documented and observed notification evidence. The report separates delivery evidence from unproven read evidence and states limits; the applicable content review is recorded. It can finish even if "Is delivery evidence sufficient?" is still pending. If R1 had promised proof of a supported read receipt, that criterion would remain unverified; time spent cannot make it pass.

## Review can finish with rejection

Review V1 inspects candidate c18 against C1 revision 2 and finds the save-failed state shows success. V1's honest rejection completes the review. The producing work stays unaccepted for that criterion. The worker fixes it as c19, keeps the rejection, re-runs affected evidence and every full gate required. A pass on c17 or a screenshot from c18 is not a pass on c19.

## Changed agreement requires an explicit evidence assessment

If C1 changes from revision 2 to 3 by adding shared filters, the personal-only isolation check does not verify shared-filter permissions. Record the authority, new criteria, affected work and required checks. Do not silently reuse the old acceptance or dispatch new scope from the old task. Likewise, a move to a newer version of the method is explicit; active work does not change because a newer version exists, and mandatory repository and security rules still govern.

## Minimal recoverable completion record

"C1 revision 2; method human-agent-development; RP1 revision 7. Candidate c17 in T1 passed the linked round-trip, failed-save, isolation and RP1 quality/review checks recorded by Sam at t3 in the task result and comments. Alex accepted this candidate scope at t4. No deployment performed or promised. No unresolved C1 blocker. Next: an authorized release worker can evaluate c17 under the release contract."

In real work replace every fictional reference with actual readable artifacts, observed revisions and authorized identities.
